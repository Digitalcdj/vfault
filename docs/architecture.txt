# VFault — Verification at the Fault Lines

**A working architecture for structurally honest AI — with prototype, benchmarks, and competitive analysis**

Ian Fraser — Exceed Web Services
August 2026

---

## Abstract

Current large language models deliver every output — verified fact, educated guess, and outright fabrication — with identical confidence. The user has no way to distinguish between them without already knowing the answer.

VFault is a working architecture that separates the language model's reasoning capability from the responsibility of being factually correct. It introduces a deterministic verification layer between the model and the user, backed by a knowledge store of structured triples parsed directly from authoritative source code. Every claim is categorised as either **verified** or **contested**, with different output behaviours for each.

Unlike every major competitor in the hallucination detection space — which use LLMs to judge LLMs — VFault uses deterministic lookup against actual source code. No AI in the verification layer. Binary result. Correction provided. Under 1ms. Zero false positives.

A working prototype of the WordPress shard has been built and tested: 25,398 triples, 4,591 functions, 2,346 hooks. Tested against three frontier models (Grok, Gemini, Claude) across standard and hard questions. On hard edge-case questions, Claude hallucinated 4 function names — the gate caught all 4 with correction suggestions. On deliberately fabricated input, 100% catch rate.

This is a working system with measured results, production guardrails, and a clear competitive advantage within deterministic domains — any domain where a source of truth exists and can be parsed.

## 1. The Problem

Language models predict plausible text, not verified facts. Confidence and accuracy are completely decoupled. The model produces equally authoritative text regardless of whether the underlying signal is strong or weak.

A 2025 MIT-linked study found that AI models use more confident language when hallucinating than when giving factual information. A May 2026 EPFL paper demonstrated that models verify facts more reliably than they generate them, and can enter a "multi-verse" state where they verify contradictory answers as simultaneously correct.

The industry's response has been to use LLMs to judge LLMs. Every major hallucination detection tool — Galileo Luna, Patronus Lynx, Braintrust, Arize Phoenix — uses a fine-tuned model or an LLM-as-judge to score outputs. The judge can hallucinate too. The scores are probabilistic. No corrections are provided.

VFault takes a fundamentally different approach: deterministic verification against the actual source of truth.

---

## 2. The Core Insight

For any factual claim in a deterministic domain, the answer space is finite and bounded. A WordPress function either exists or it doesn't. A parameter signature is correct or it isn't. A function is deprecated or it's active.

Not all knowledge is equal. Some claims are settled and verified. Others are genuinely contested among experts. These require different treatment:

- **Verified:** state the fact directly, no hedging.
- **Contested:** present the positions and evidence, let the user decide.

The model never decides which category a claim belongs to. That is metadata in the knowledge layer.

## 3. Architecture — Three-Agent Streaming Pipeline

### 3.1 Agent 1 — The Generator
Any LLM (Claude, GPT, Grok, Gemini). Generates the response and tags its own factual claims. Does not verify anything. One objective: be helpful.

### 3.2 Agent 2 — The Resolver-Assembler
Deterministic lookup engine. Checks tagged claims against the hot-cached triple store in real time during generation. For deterministic domains, "not found in store" IS the verification. No LLM needed.

Converts claims to structured triple queries, checks hot cache (microseconds) then domain-sharded store (milliseconds), applies verification results immediately: confirmed, corrected, contested, or flagged as unverified.

### 3.3 Agent 3 — The Verifier
Fires only for non-deterministic domains (medical, legal, emerging science). Architecturally independent from Agent 1 — different model, different provider, rotating pool. Optimised for scepticism.

Not needed for the WordPress shard. WordPress is deterministic.

### 3.4 Pipeline

```
User query
    |
    v
[Agent 1: Generator] — streams response + claim tags
    |
    v
[Agent 2: Resolver-Assembler]
    |
    Hot cache (microseconds) → DB fallback (milliseconds)
    |                               |
    Found                       Not found
    (confirm/correct)               |
    |                    [Deterministic domain?]
    |                      Yes            No
    |                       |              |
    |                  "Not found      [Agent 3: Verifier]
    |                   = wrong"       (parallel, batched)
    |                       |              |
    v                       v              v
[Response with verification metadata]
```

## 4. Working Prototype — WordPress Shard

### 4.1 What was built

**Parser (shards/wordpress/parser.py):** Parses WordPress GitHub source, extracts every function, hook, parameter, return type, version, and deprecation status into structured triples in SQLite.

**Store (wordpress.db):** 25,398 verified triples. 5.8 MB.

| Category | Count |
|---|---|
| Functions (active) | 4,192 |
| Functions (deprecated) | 402 |
| Hooks (actions) | 610 |
| Hooks (filters) | 1,736 |
| Class methods (wpdb, WP_REST_Request, WP_Query) | 27 |

**Gate (vfault.py):** FastAPI + CLI. Six endpoints. Hot-cached store for microsecond lookups. Context-aware claim extraction (0% false positives). Parameter comparison. Deprecation tracking with replacement suggestions. Fuzzy matching with correction suggestions.

**Build cost:** £0.

### 4.2 Gate capabilities

- Function existence verification against parsed source code
- Hallucination detection with closest-match suggestions
- Deprecation detection with replacement function named
- Parameter signature comparison (catches outdated params)
- Class method recognition (wpdb, WP_REST_Request, WP_Query)
- Context-aware extraction (filters out capability strings, user-defined hooks, variable names)

### 4.3 Production guardrails

- Input size limit: 50,000 characters max
- Rate limiting: 100 requests per minute per IP
- Name sanitisation: strips SQL injection attempts, special characters
- Invalid input rejection: empty or malformed names return 400
- Search result cap: max 50 results
- Field length limits on all inputs

## 10. Optimisations

- Streaming verification during generation
- Hot cache for microsecond lookups
- Deterministic domain shortcutting (Agent 3 skipped for code/API domains)
- Context-aware extraction eliminating false positives
- Failure-mapped store built from known error patterns
- Cascading verification: six levels from cache to human review
- Error-feedback loops: store grows from real usage failures
- Community contestation: verified/contested boundary governed via PR model
- Well-memorised falsehood detection via known-falsehood registry

---

## 11. Limitations

**Coverage gap:** novel or contextual queries won't be in the store. Error-feedback narrows this over time.

**Claim identification is imperfect:** context-aware extraction catches most false positives but won't catch every factual claim embedded in reasoning.

**Deterministic domains only (for now):** VFault's core advantage applies where a source of truth exists. Non-deterministic domains require Agent 3.

**Reasoning errors out of scope:** catches wrong facts, not wrong logic.

**Distribution is the primary risk:** the technical foundation is sound. Whether developers adopt it depends on packaging, visibility, and sustained effort — not on whether the approach works.

**Bigger players can replicate:** once the deterministic pattern is proven, larger companies (GitHub, Cursor, Sourcegraph) could build similar checks. Speed to market and community matter.

**Not a replacement for better models:** complementary infrastructure.
